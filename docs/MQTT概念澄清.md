# MQTT 概念澄清：协议、软件、端口、主题与网络通路

本文回答"这些名词到底谁是谁、各自干什么活"，全部结论都对应到本项目的实际配置与实测现象。
阅读目标：以后任何"MQTTX 收不到数据"，能 30 秒内判断卡在哪一层，而不是反复重启热点。

---

## 0. 一页速查

| 名词 | 本质 | 在本项目里的对应物 | 一句话 |
|---|---|---|---|
| **MQTT** | 协议（一份文档） | 板子和 MQTTX 凭什么能对话 | 定规矩的，不能启动、不占端口 |
| **EMQX** | Broker 服务器软件 | 本机 `erl.exe`，监听 1883 | 干活的，按订阅名单转发 |
| **amqtt** | 另一个 Broker 软件 | `tools/mqtt_lab/broker.yaml` | 同一份协议的替代实现，与 EMQX 互斥 |
| **MQTTX** | 客户端 GUI 软件 | 你用来订阅查看的窗口 | 只连 Broker，不能替代 Broker |
| **esp-mqtt** | ESP-IDF 的协议库 | 板子固件里发 PUBLISH 的代码 | 客户端那一半的实现 |
| **1883** | TCP 端口号 | 三处配置必须一致 | 门牌号，不是功能 |
| **移动热点** | 网卡角色（接入点 + DHCP） | `本地连接* 2`，`192.168.137.1` | 让板子能进门 |
| **主题** | 字符串寻址 | `dev/intern01/data` | 发布/订阅之间唯一的耦合点 |

记忆口诀：**协议定规矩，软件干活，端口负责找得着，热点负责进得来。**

## 1. MQTT 是协议，EMQX 是实现

**是什么**
MQTT 是一份规定了报文二进制格式、握手顺序、确认机制的规范文档（当前主流版本 3.1.1 与 5.0）。
它本身不可执行：没有进程、不监听端口、装不上也停不掉。EMQX 是**遵守这份规范**写出来的一个服务器程序。

**在你项目里**

| 对比项 | MQTT | EMQX |
|---|---|---|
| 形态 | 文档 / 约定 | 安装包 + 可执行文件 |
| 有没有进程 | 没有 | 有（`erl.exe`） |
| 占不占端口 | 不占 | 占 1883、18083 |
| 能不能换 | 不能"换协议"，只能换版本 | 能换成 amqtt / Mosquitto，两端代码不用改 |
| 出错表现 | 报文格式错 → 被 Broker 直接断连 | 没启动 → 连接被拒 / 超时 |

**搞错会怎样**
把"启动 EMQX"理解成"启用 MQTT"，就会以为 MQTT 是个开关。实际是：你启动了一个**会说 MQTT 的服务程序**。同理，MQTTX 不是"MQQT 的客户端版本"，它是一个**客户端软件**，只实现协议里客户端那一半（CONNECT / PUBLISH / SUBSCRIBE），没有转发能力。

**一句话排查**
"连不上"先问：是**没有 Broker**（服务没起），还是**客户端说错了话**（主题、账号、协议版本不对）。前者看进程和端口，后者看 Broker 日志。

## 2. 端口 1883：把包交给哪个进程

**是什么**
TCP 端口号，作用是把数据包定位到**某台机器上的某个进程**。IP 负责找到机器，端口负责找到程序。

一条 TCP 连接由四元组唯一确定：

```
源 IP:源端口  →  目的 IP:目的端口
192.168.137.140:52341  →  192.168.137.1:1883
```

- 目的端口 `1883` 固定，由 EMQX 启动时 `bind()` 登记；
- 源端口 `52341` 由板子系统随机分配，每次重连都可能变；
- 所以 Dashboard 里同一个 IP 会出现多个会话——源端口不同，四元组就不同。

端口范围 `0 ~ 65535`，其中 `0 ~ 1023` 是 IANA 统一分配的知名端口，1883 就在这个区间内，专属于 MQTT 明文传输。

**在你项目里**

| 端口 | 用途 | 本项目状态 |
|---|---|---|
| **1883** | MQTT over TCP，明文 | 使用中 |
| 8883 | MQTT over TLS | 未启用（需证书 + TLS 组件） |
| 8083 | MQTT over WebSocket | 未启用（浏览器 JS 客户端才需要） |
| 8084 | MQTT over WSS | 未启用 |
| **18083** | EMQX Dashboard 网页 | 使用中，`http://localhost:18083` |

1883 与 18083 毫无关系：前者给机器连，后者给人看。关掉 1883 网页照样能打开，只是看不到设备在线。

三处配置必须完全一致，任何一处写错都连不上：

| 位置 | 当前值 | 改它的代价 |
|---|---|---|
| EMQX 监听 | `0.0.0.0:1883`（默认） | 改 `emqx.conf` 后重启 |
| 固件 `sdkconfig` | `mqtt://192.168.137.1:1883` | 重新编译 + 烧录 |
| MQTTX 连接设置 | Host `192.168.137.1`，Port `1883` | 改完点重连 |

`0.0.0.0` 表示监听本机所有网卡地址，等价于"任何能到达本机的地址都接受"。若配成 `127.0.0.1`，则只有本机能连，板子必然超时——这是新手高频坑。

**搞错会怎样**
端口是**独占**的：同一时刻只能有一个进程监听。这就是 amqtt 与 EMQX 不能同时运行的原因：

```
amqtt 先启动 → 占住 1883
EMQX 后启动 → bind 失败 → 报 address already in use 后退出
```

EMQX 启动输出里那些 `EMQX_NODE__DB_ROLE` / `EMQX_NODE__DB_BACKEND` 的打印是 `emqx.cmd` 里 `set` 语句的 echo 回显，**不是错误**，别被它误导成"启动失败"。

**一句话排查**

| 现象 | 含义 | 排查方向 |
|---|---|---|
| 连接**被拒绝**（立刻返回 RST） | 目标 IP 通，但该端口没人监听 | 端口写错、服务没启动、被别的程序占了 |
| 连接**超时**（长时间无响应） | 包没到，或到了被静默丢弃 | 防火墙、网段不通、IP 写错 |

```powershell
netstat -ano | findstr ":1883"
```

最后一列是 PID，到任务管理器对照：`erl.exe` 是 EMQX，`python.exe` 是 amqtt，就知道该停哪个。

## 3. 网络通路：三个关卡，三个不同的故障现象

**是什么**
数据包从板子到 EMQX，要连过三关，每关由不同机制负责，互相独立：

```
板子 ESP32-C3 (192.168.137.140)
    |
    |  第 1 关  能不能关联上 Wi-Fi？            <- 移动热点（SSID + 认证）
    v
电脑无线网卡 192.168.137.1（热点角色）
    |
    |  第 2 关  能不能拿到地址、路由对不对？      <- 热点内置 DHCP
    v
Windows 网络栈
    |
    |  第 3 关  1883 端口的入站包让不让进？       <- Windows 防火墙入站规则
    v
EMQX 进程（软件角色，listening 0.0.0.0:1883）
```

**在你项目里**

热点（Windows 移动热点 / ICS 连接共享）做了三件事：

| 作用 | 具体行为 | 少了的后果 |
|---|---|---|
| ① 无线接入 | 网卡广播 SSID，板子以 STA 身份关联 | 板子无网口，进不了网络 |
| ② 分配 IP | 内置 DHCP 派发 `192.168.137.2` 起 | 卡在 `wifi_wait_connected` 超时 |
| ③ 网关转发 | 自身为 `192.168.137.1`，负责网段内互通 | 包到不了本机协议栈 |

`192.168.137.1` 是 Windows ICS 的**硬编码约定**，不是随意指定：启用共享后系统固定把共享网卡配成 `192.168.137.1/24`。

由此得到一个很实用的结论：**热点关掉再开、电脑重启、板子断电重连，板子 IP 可能从 `.140` 变成 `.141`，但电脑永远是 `192.168.137.1`。** 所以固件里的 MQTT 地址一次写死，之后不用再改。

**搞错会怎样**

- **"板子连上 Wi-Fi 了"不等于"能连上 EMQX"**。串口打印 `got ip:192.168.137.140` 只说明第 1、2 关过了，第 3 关还完全没验证。本项目实测就是卡在第 3 关：1883 入站规则不存在，三个 profile 全开启，包被静默丢弃，表现为长时间无响应。
- 第③项"转发到公网"在本项目**用不到**：EMQX 就在本机，板子访问 `192.168.137.1` 属于网段内访问，不出公网。但若哪天换成云端 Broker（阿里云/华为云），热点就必须真的能上外网。
- 不必用手机热点：那样电脑 IP 由手机随机分配，换一次热点就要重新编译烧录固件；且部分手机热点开启 AP 隔离，客户端之间互不可见。
- Windows 移动热点默认会在**一段时间无客户端连接后自动关闭**。长时间调试建议到「设置 → 网络和 Internet → 移动热点」关掉自动关闭，否则会出现板子莫名掉线、串口反复 `reason=201` 重连。

**一句话排查**

| 卡点 | 判断依据 | 通过标志 |
|---|---|---|
| 第 1、2 关 | 板子串口 | `wifi connected` + `got ip:192.168.137.x` |
| 电脑侧网卡 | `ipconfig` | `本地连接* 2` 为 `192.168.137.1` |
| 第 3 关（服务） | `netstat -ano \| findstr :1883` | `0.0.0.0:1883 LISTENING` |
| 第 3 关（防火墙） | 管理员 PowerShell 加规则 | `netsh advfirewall firewall show rule name="MQTT 1883"` 有输出 |

添加防火墙规则（需管理员权限）：

```powershell
netsh advfirewall firewall add rule name="MQTT 1883" dir=in action=allow protocol=TCP localport=1883
```

## 4. 主题与订阅：发布者根本不知道谁在听

**是什么**
MQTT 用字符串"主题"做寻址，一帧 PUBLISH 里只有主题名，没有收件人地址。Broker 收到后遍历订阅表，把消息拷贝给所有匹配的订阅者；**匹配不到就丢弃**。

**在你项目里**

| 角色 | 主题 | QoS |
|---|---|---|
| 板子发布 | `dev/intern01/data` | 1 |
| MQTTX 订阅 | `dev/intern01/#` | 1 |

通配符只有两个：

| 写法 | 含义 | 例子 |
|---|---|---|
| `#` | 匹配剩余所有层级，必须放最后 | `dev/intern01/#` 命中 `dev/intern01/data`、`dev/intern01/a/b` |
| `+` | 只匹配一层 | `inverter/+/data` 命中 `inverter/collector/data`，不命中 `inverter/a/b/data` |

**搞错会怎样**

整个系统里，**两端唯一的耦合点就是主题字符串**。板子端写在 `sdkconfig` 编译进固件，MQTTX 端是运行时手填。只改一边，现象就是"串口一切正常、MQTTX 一条不显示"，极易误判为固件坏了。

MQTTX 的气泡颜色与 QoS 无关，只表示归属：绿色是本客户端发出，灰色是收进来的。手打 JSON 带空格（`"voltage": 10.0`），`cJSON_PrintUnformatted` 输出无空格（`"voltage":10.0`），可据此区分来源。

**一句话排查**
Dashboard 看 `messages.dropped`：发布成功但 dropped 在涨 → 没人订阅或主题不匹配，与网络无关。

## 5. 一次完整上报的报文级旅程

从寄存器到屏幕，全链路分段如下（本项目实测值）：

| 阶段 | 动作 | 实测数据 |
|---|---|---|
| ① Modbus 请求 | 读 5 个保持寄存器，起始 `0x3000` | `01 03 30 00 00 05 8A C9` |
| ② Modbus 应答 | 返回 10 字节数据 | `01 03 0A <10B> <CRC>` |
| ③ 换算 | `÷10` 电压、`÷100` 电流、`÷1` 功率 | `3500→350.0` `500→5.00` `1750→1750` |
| ④ 门控 | 连续成功 ≥ 3 次才允许上报 | 最快 15 秒出第一条 |
| ⑤ 组包发布 | PUBLISH QoS1 到主题 | 见下方字节拆解 |
| ⑥ Broker 转发 | 按订阅表匹配后拷贝 | MQTTX 收到同一份 JSON |
| ⑦ 确认 | EMQX 回 PUBACK | 板子认为本轮发布成功 |

PUBLISH 帧逐字节：

```
32 48 00 17 69 6E 76 65 72 74 65 72 2F ... 00 01 7B 22 ...
|  |  |--+--| |-----------+-----------| |--+--| |------+------|
|  |  主题长度 23   主题名 23 字节     报文标识符  JSON 45 字节
|  +- 剩余长度 0x48 = 72
+---- 0x3X = PUBLISH，低 2 位 0b10 = QoS 1
```

剩余长度 72 = 2（主题长度字段）+ 23（`inverter/collector/data`）+ 2（报文标识符）+ 45（JSON）。
报文标识符把这条 PUBLISH 与回来的 PUBACK 配对，也是串口日志里 `msg_id=41144` 的来源，计到 65535 后绕回。

**QoS 1 的含义是"至少一次"**：EMQX 收到即回 `0x40 PUBACK`（剩余长度 2，带回同一标识符）。QoS 0 则发完不管，丢了也不知道——所以上报用 1。

**实测闭环**：串口 `msg_id=41144` 对应的正是 MQTTX 收到的 `{"voltage":350.0,"current":5.00,"power":1750}`，与寄存器 `3500 / 500 / 1750` 完全对得上。

## 6. 常见误区集中澄清

| 说法 | 是否正确 | 实际情况 |
|---|---|---|
| "启动 EMQX 就等于启用了 MQTT" | ✗ | MQTT 是协议，没有开关；你启动的是会说 MQTT 的服务程序 |
| "MQTTX 是 Broker 的图形版" | ✗ | 它只是客户端，没有 Broker 时连不上任何东西 |
| "板子连上 Wi-Fi 就能发数据了" | ✗ | Wi-Fi 只过了两关，还有防火墙与 Broker 两关 |
| "板子在线但 recv_msg=0 是网络问题" | ✗ | 多半在 Modbus 侧或上报门控，网络反而已通 |
| "EMQX 会把消息存下来等我连上" | ✗ | 默认不存，无人订阅即丢弃（保留消息/持久会话需额外配置） |
| "换 Broker 要重烧固件" | ✗ | 同一份 MQTT 协议，amqtt → EMQX 固件零改动 |
| "改了 MQTTX 的订阅主题，板子也要改" | ✗ | 板子只管发，接收方自己订阅即可 |
| "1883 和 18083 是同一个东西" | ✗ | 1883 给机器连，18083 给人看网页 |

**关于门控的补充**（"MQTTX 已连接却没数据"最常见原因）：

```c
if (modbus_read_registers(...)) consecutive_ok++;   // 成功 +1
else                           consecutive_ok = 0;  // 失败清零

if (!reporting && consecutive_ok >= 3) reporting = true;
```

推论：
1. 烧完板子最快 15 秒（5 秒 × 3 次）才有第一条数据；
2. 串口若反复出现 `read failed, retry next cycle (ok=0, err=...)`，则永远不上报，与网络无关；
3. 开机自检是**同步阻塞**在 `app_main` 里的，`xTaskCreate(collector)` 在其之后，自检那 45 秒内一条数据也不会发。

## 7. 排查口诀

> 先看串口，再看端口，最后看防火墙。

| 顺序 | 看什么 | 定位到的层 |
|---|---|---|
| 1 | 串口有没有 `collector task started` | 是否还卡在开机自检 |
| 2 | 串口有没有 `reporting started` / `read failed` | Modbus 段 与 上报门控 |
| 3 | 串口有没有 `broker connected` | 网络段（热点 / IP / 防火墙） |
| 4 | `netstat -ano \| findstr :1883` | Broker 是否在听 |
| 5 | Dashboard 的 `messages.dropped` | 主题是否匹配、是否有人订阅 |

反向排查（先查网络再看串口）会白花大量时间：只要 `read failed` 还在刷，网络再通也不可能收到数据。
