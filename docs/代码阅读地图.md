## 一、先分清「看不懂」的三种情况

大部分人说自己看不懂代码，其实混了三件不同的事：

| 类型 | 典型表现 | 本质 | 该怎么办 |
|---|---|---|---|
| **不认识 API** | "`uart_read_bytes` 四个参数是啥意思" | 缺函数签名知识 | 查文档，**不算能力问题** |
| **不认识语法** | "`(rx[1] & 0x80)` 在干嘛" | 缺 C 语言基础 | 补位运算、指针、数组 |
| **不认识业务意图** | "为什么发之前要清空缓冲？" | 缺领域经验 | **这才是要花时间的地方** |

这个工程 2403 行，其中 60% 是 API 调用和配置，看一眼文档就懂。真正需要"想明白"的只有 300~400 行。

**所以不要从头到尾读**。按下面的顺序走，两小时能有整体把握。

## 四、四个必须吃透的函数，逐行拆解

### 4.1 `modbus_transact_locked()` —— 全工程的核心

`modbus.c:197`，70 行。所有功能码都复用它，搞懂这 70 行，Modbus 就通了。

```c
static bool modbus_transact_locked(uint8_t slave, uint8_t func,
                                   const uint8_t *tx, int tx_len,
                                   uint8_t *rx, int rx_cap, int rx_expect, int *rx_len)
{
    s_last_exception = 0;

    for (int attempt = 0; attempt <= MODBUS_RETRY_COUNT; attempt++) {

        if (attempt > 0) {
            vTaskDelay(pdMS_TO_TICKS(MODBUS_RETRY_GAP_MS));
        }

        uart_flush_input(MODBUS_UART_PORT);          /* ① 清残留 */

        modbus_log_hex("TX", tx, tx_len);
        uart_write_bytes(MODBUS_UART_PORT, (const char *)tx, tx_len);   /* ② 发 */

        int len = uart_read_bytes(MODBUS_UART_PORT, rx, rx_cap,
                                  pdMS_TO_TICKS(MODBUS_TIMEOUT_MS));    /* ③ 等 */
        if (len <= 0) {
            ESP_LOGW(TAG, "func 0x%02X timeout (attempt %d/%d)", ...);
            continue;
        }

        modbus_log_hex("RX", rx, len);

        /* ④ 异常应答：功能码最高位置 1，长度固定 5 */
        if (len >= 5 && (rx[1] & 0x80)) {
            s_last_exception = rx[2];
            ESP_LOGE(TAG, "slave exception: code=0x%02X (%s)", ...);
            return false;                              /* 从机明确拒绝，重试无意义 */
        }

        if (len < rx_expect) { continue; }              /* ⑤ 帧被截断 */

        if (rx[0] != slave || rx[1] != func) { continue; }   /* ⑥ 地址/功能码不符 */

        uint16_t rx_crc = (uint16_t)rx[len - 2] | ((uint16_t)rx[len - 1] << 8);
        uint16_t calc   = modbus_crc16(rx, (uint16_t)(len - 2));
        if (calc != rx_crc) { continue; }               /* ⑦ CRC 校验 */

        *rx_len = len;
        return true;
    }

    return false;
}
```

**七个动作，每一个都有理由：**

| 步骤 | 为什么 |
|---|---|
| ① `uart_flush_input` | 清掉上一轮超时后迟到的应答。不清的话，这次读到的可能是**上次**的数据——CRC 能过、数值是旧的，这种 bug 最难查，因为日志看起来一切正常 |
| ② 先打日志再发 | 出问题时能看到"我发了什么"，顺序反了就看不到失败的帧 |
| ③ 带超时读 | 不能死等。9600 波特率下一帧 8 字节约 9ms，超时设 200ms 已很宽松 |
| ④ 异常帧先判 | 从机拒绝时回的是 5 字节短帧，功能码 OR 0x80。这种情况**重试没用**，要立即返回并把异常码存下来 |
| ⑤ 长度检查 | 收到的比预期短，说明帧被截断（线路干扰、波特率不匹配） |
| ⑥ 头校验 | 总线上可能有别的设备的应答串进来 |
| ⑦ CRC 校验 | 最后一道防线。前面都过了但 CRC 错，说明传输过程中有比特翻转 |

**关键设计**：`continue` 表示"这次失败，再试一次"，`return false` 表示"彻底失败"。第 ④ 步用 `return`，其他用 `continue`——这个区分很多人第一次读会忽略。

### 4.2 `modbus_read_regs()` —— 响应怎么解成数值

`modbus.c:368`

```c
int tx_len    = modbus_build_read_request(slave, func, addr, num, tx);
int rx_expect = 5 + num * 2;      /* 地址1 + 功能码1 + 字节数1 + 数据2n + CRC2 */

if (!modbus_transact(...)) { return false; }

if (rx[2] != num * 2) {           /* 从机回报的字节数必须对得上 */
    return false;
}

for (uint16_t i = 0; i < num; i++) {
    /* 大端序：高字节在前 */
    regs[i] = (uint16_t)(((uint16_t)rx[3 + i * 2] << 8) | rx[4 + i * 2]);
}
```

响应帧布局：

```
rx[0]      从机地址
rx[1]      功能码
rx[2]      后续数据字节数 = num × 2
rx[3..4]   第 1 个寄存器（高字节在前）
rx[5..6]   第 2 个寄存器
...
rx[len-2]  CRC 低字节
rx[len-1]  CRC 高字节
```

注意 **CRC 是低字节在前，寄存器数据是高字节在前**——两个相反的字节序，这是 Modbus 最反直觉的地方。

### 4.3 `collector_task()` 的主循环

`inverter_collector.c:71`

```c
while (1) {
    bool wifi_ok = wifi_is_connected();

    bool ok = modbus_read_registers(REG_BASE, REG_COUNT, regs);

    if (ok) {
        ok_cnt++;
        consecutive_ok++;
        voltage = regs[IDX_VOLTAGE] / 10.0f;      /* 整数除法会丢精度，必须 .0f */
        ...
        if (!reporting && consecutive_ok >= REPORT_START_THRESHOLD) {
            reporting = true;                      /* 连续成功 3 次才开始上报 */
        }
        if (reporting && wifi_ok) {
            mqtt_report_send_json(voltage, current, power, 0);
        }
    } else {
        err_cnt++;
        consecutive_ok = 0;
        /* 读失败也要上报，带 state=1 和上次的数值 */
        if (reporting && wifi_ok && has_last && mqtt_report_is_connected()) {
            mqtt_report_send_json(last_voltage, last_current, last_power, 1);
        }
    }

    vTaskDelay(pdMS_TO_TICKS(COLLECT_PERIOD_MS));
}
```

三个设计点：

1. **`consecutive_ok >= 3` 才上报**：开机时前几秒的读可能因从机还没就绪而失败，等稳定了再发数据，避免上位机收到一串 0
2. **`/ 10.0f` 不是 `/ 10`**：整数除法会截断，`3500/10` 得 350 没问题，但 `3505/10` 得 350 而不是 350.5
3. **失败也上报**：不带 `state=1` 的话，上位机分不清"设备掉线"和"网络抖动"

### 4.4 `mqtt_cmd_handle_message()` —— 三层校验的顺序

`mqtt_cmd.c:353`

```c
if (data_len >= CMD_MAX_PAYLOAD) { return; }        /* ① 先判长度 */

if (topic_is(topic, topic_len, MQTT_TOPIC_WRITE)) { is_write = true; }
else if (topic_is(topic, topic_len, MQTT_TOPIC_READ)) { is_write = false; }
else { return; }                                     /* ② 再判主题 */

char payload[CMD_MAX_PAYLOAD];
memcpy(payload, data, data_len);
payload[data_len] = '\0';                            /* ③ 补 '\0' */

handle_cmd(is_write, payload);                       /* ④ 进业务层解析 */
```

顺序不能换的三个理由：

- **长度必须最先判**：缓冲区是栈上定长的，判晚了就已经溢出了
- **主题必须按长度比**：`event->topic` 不以 `\0` 结尾，用 `strcmp` 会读越界
- **`payload[data_len] = '\0'` 必须补**：MQTT 载荷是二进制安全的字节流，cJSON 需要 `\0` 才能解析

## 五、五个自测题

能全答上来，第一档就算过了。

### Q1：波特率从 9600 改成 115200，要改几处？

**答**：固件里一处——`modbus.c` 的 `MODBUS_BAUDRATE` 宏（或 menuconfig）。

但**从机那侧也必须改**，否则一直超时。这是最常被忽略的一半：两台设备波特率不一致时，收到的全是乱码，CRC 必然失败，日志刷 `CRC mismatch` 或 `timeout`。

### Q2：日志出现 `short frame: got 5 expect 7` 说明什么？

**答**：收到 5 字节，预期 7 字节。

可能原因：
- 帧被截断（线路干扰、接触不良）
- 从机功能码和请求不一致，回了异常帧（但异常帧会先被第 ④ 步拦截，所以排除）
- 波特率不匹配导致采样点错位，丢字节

排查顺序：先确认波特率一致 → 再查接线 → 最后考虑加终端电阻。

### Q3：为什么发之前要 `uart_flush_input`？

**答**：清掉上一轮超时后迟到的应答。

举个具体场景：第 1 次请求超时了，但应答在第 250ms 才到（超过 200ms 超时）。第 2 次请求发出去后，`uart_read_bytes` 读到的第一条正是**第 1 次的旧应答**。

如果不清缓冲，这次会"成功"——CRC 对、长度对、地址对，但数值是上一次的。上位机看到数据正常，实际是错的。

### Q4：采集任务和命令任务同时读串口会怎样？

**答**：两帧交错，CRC 必然失败，表现为**随机**的 `read failed`（不是每次必现，取决于时序）。

因为 `uart_write_bytes` 是非阻塞的，采集任务发完帧去读的时候，命令任务可能正插进来发自己的帧。两个请求的应答混在一起，接收缓冲里就是交错的字节流。

解决：总线互斥量，且**锁的粒度必须覆盖整个事务**（清缓冲 → 发 → 收 → 校验 → 重试）。只锁发送是无效的，因为接收阶段同样共享缓冲区。

### Q5：为什么 MQTT 回调里不能直接读 Modbus？

**答**：会把连接拖断。

算一下时间：

```
一次读最坏 = 200ms 超时 × 3 次尝试 + 2 × 20ms 重试间隔 ≈ 640ms
keepalive  = 60 秒，Broker 在 1.5 倍（90 秒）无心跳才判定离线
```

单看 640ms 远小于 90 秒，似乎没问题。但 MQTT 回调运行在 esp-mqtt 自己的任务里，**回调阻塞期间它无法处理任何收包**。如果上位机连续发 10 条命令，就是 6.4 秒不响应心跳；网络再有点抖动，很容易累积到被踢。

而且回调阻塞还会导致：
- 收不到 PUBACK → Broker 重传 → 更多消息堆积
- 订阅的其他主题全部积压

所以回调只做"传达室"：**验长度 → 判主题 → 解析 → 入队**，立刻返回（<1ms）。真正的 Modbus 读写放在 `cmd_task` 里慢慢等超时。

## 七、附录：怎么让 AI 写第四档的代码

关键不是"帮我写个函数"，而是**把约束说清楚**。模板：

```text
用 ESP-IDF 5.5 写一个 [功能]，要求：

输入：[参数类型、取值范围]
输出：[返回值含义、错误码]
约束：
  - 不使用动态内存（或说明在哪里释放）
  - 所有输入必须校验边界，越界返回错误而不是断言
  - 解析失败时不要 return 0，要返回明确错误码
  - 日志用 ESP_LOGx，TAG 叫 XXX
不要做什么：[例如不要在这里做耗时 IO]
```

好的请求 vs 差的请求：

| 差 | 好 |
|---|---|
| "写个 Modbus 读函数" | "用 ESP-IDF 写功能码 03 的读保持寄存器，输入从机地址 1~247、寄存器地址 0~65535、数量 1~16，返回 bool，失败要区分超时和从机异常码" |

**判断标准**：如果生成的代码你没法验收（不知道对不对），说明需求描述本身有问题，先想清楚再让 AI 写。

反过来，**第一档的代码不要让 AI 代写**。不是怕它写错，而是那些细节（为什么要 flush、为什么异常帧要 return 而不是 continue）只有自己踩过坑才记得住，而现场排查靠的正是这些记忆。
