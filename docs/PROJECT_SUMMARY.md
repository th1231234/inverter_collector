## 摘要

一个"读寄存器 → 上报云端"的设备端程序，分三个阶段递进：**Modbus RTU 采集 + UDP 上报**（阶段一）、**MQTT 四主题双向通信**（阶段二）、**Protobuf 二进制遥测**（阶段三）。

三个阶段全部跑通并通过自测：

| 阶段 | 主题 | 用例 | 结果 | tag |
|---|---|---|---|---|
| 阶段一 | Modbus RTU + UDP 上报 | 验收流程 6 步 + 加分项 | 通过 | `stage1` |
| 阶段一点五 | 追加 TCP 通道 + 开机功能码自检 | 7 项功能码自检（4/7 通过，其余为从机侧限制） | 通过 | — |
| 阶段二 | MQTT 查询 / 上报 / 修改 | M-01 ~ M-08 全部 PASS | 基础功能 100/100 | `stage2` |
| 阶段三 | Protobuf 上传与解析 | P-01 ~ P-07 全部通过 | 通过 | `stage3` |

**规模**：固件手写代码 2853 行（另有 protoc 生成的 929 行）、测试脚本 1976 行、文档 3200 行、Git 提交 18 次。

**技术要点**：手写 CRC16-Modbus、事件驱动 Wi-Fi 重连、FreeRTOS 任务与队列、UART 总线互斥、MQTT QoS1 与请求应答配对、protobuf-c 编解码、SNTP 对时、分区表调整。

## 一、项目背景与目标

逆变器现场设备需要把电压、电流、功率等运行参数采集上云。工程实现一个采集器：通过 UART 以 Modbus RTU 协议读取逆变器的保持寄存器，换算成物理量后经 Wi-Fi 上报。逆变器侧用 Modbus Slave 软件仿真，无需真实硬件。

三个阶段的能力递进很明确：

| 阶段 | 新增能力 | 关键技术 |
|---|---|---|
| 一 | 能采、能发 | Modbus RTU、CRC16、Wi-Fi STA、UDP |
| 一点五 | 能可靠地发 | TCP 长连接与半关闭处理、功能码自检 |
| 二 | 能被查询、能被修改 | MQTT 发布订阅、JSON、队列解耦、总线互斥 |
| 三 | 报文更小、结构更强约束 | protobuf、varint 编码、二进制长度语义 |

## 二、硬件与软件环境

### 2.1 硬件

| 器件 | 说明 |
|---|---|
| ESP32-C3 开发板 | 主控，4MB Flash，单核 RISC-V |
| TTL 转 RS485 模块 | 板载，自动收发方向（无 DE 脚） |
| USB 转 RS485 模块 | 电脑侧接 Modbus Slave |
| USB 转 TTL 线（PL2303） | 烧录 + 日志，COM8 |

### 2.2 接线与串口分配

| 用途 | 引脚 | 电脑侧 | 参数 |
|---|---|---|---|
| Modbus 采集（UART1） | TX = GPIO23，RX = GPIO39 | COM10 | 9600-8-N-1，从机 1 |
| 调试日志（UART0） | 板载 USB | COM8 | 115200 |

> 引脚配置用条件编译兼容两种芯片：C3 走 `UART_NUM_1` + GPIO5/6（板卡定义 23/39），经典 ESP32 走 `UART_NUM_2`。C3 上没有 `UART_NUM_2`，写死会编译失败。

### 2.3 寄存器映射

| 地址 | 参数 | 格式 | 换算 | 预设值 |
|---|---|---|---|---|
| 0x3000 | 电网电压 | uint16 | ÷10.0 | 3500 → 350.0V |
| 0x3001 | 未使用 | — | — | 0 |
| 0x3002 | 电网电流 | uint16 | ÷100.0 | 500 → 5.00A |
| 0x3003 | 未使用 | — | — | 0 |
| 0x3004 | 瞬时功率 | uint16 | ÷1 | 1750 → 1750W |

**三个参数地址步长为 2**，所以一次连续读 5 个寄存器，再按偏移 0/2/4 取值。这个细节在阶段一踩过坑（见 3.2）。

### 3.2 遇到的困难和解决过程

#### ① PL2303 串口没有 COM 号

设备管理器显示 `PL2303HXA PHASED OUT SINCE 2012`，不分配 COM 口，无法烧录。

这不是线坏了，是 Prolific 在新驱动里加了仿冒检测，检测到停产的 HXA 芯片就拒绝加载。硬件 ID `USB\VID_067B&PID_2303` 确认为真芯片。解决：装开源的 **PL2303 Legacy Driver Updater 1.1.0**，回退到 2010 年的 `3.3.11.152` 驱动。中间还卡了一次——工具报 `Device not connected`，原因是没用管理员权限运行且需要先拔插设备。

**学到的**：驱动问题先查硬件 ID 和芯片停产状态，不要急着换线。

#### ② 芯片型号误判

早期烧录日志出现 `Chip is ESP32-D0WD-V3`，据此按经典 ESP32 配了 `UART_NUM_2` + TX=23/RX=39。后来串口打出 `ESP-ROM:esp32c3-api1-20210207`，才确认是 **ESP32-C3**。C3 只有 UART0/UART1，`UART_NUM_2` 根本不存在。

处理方式不是简单改一遍，而是用条件编译同时兼容两种芯片，避免以后换板再踩。

**学到的**：芯片型号以 `esptool` 的 `Chip is ...` 和 ROM 日志为准，不能靠丝印或历史印象推断。

#### ③ 烧录链路三个叠加问题

这一阶段耗时最长，问题是**层层叠加**的，只能一个个剥离：

| 现象 | 根因 | 解决 |
|---|---|---|
| `Invalid head of packet (0x00)` | 未指定端口，自动选了错误的 COM | 显式 `-p COM8` |
| `Could not open COM5` | 插拔后 COM 号变了 | 每次烧录前重新查端口 |
| `boot:0x4 (DOWNLOAD)` + `waiting for download` | 串口助手的 DTR 拉低 GPIO9，芯片停在下载模式 | 关闭串口助手，交给 esptool |
| `No serial data received` | 四线转串口没有 RTS，`--after hard_reset` 是空操作 | 手动按住 BOOT → 点 RST，`--connect-attempts 0` 无限重试 |
| `BROWN_OUT_RST` | 供电不足 | USB 直供、短粗线、后置 USB 口 |
| 串口日志乱码 | 厂商固件波特率是 921600 | 统一 115200 |

**学到的**：DTR/RTS 不只是"自动复位"的便利，它直接决定芯片能否正常启动。四线线与六线线的差别就在这里。

#### ④ 电流/功率数值错位

第一版按题目"一次连续读 3 个寄存器"实现，结果读出来的电流、功率全是错的值。原因是逆变器正式映射里三个参数地址**步长为 2**（0x3000/0x3002/0x3004），中间两个空寄存器。读 3 个只能拿到 0x3000/0x3001/0x3002。

修正：读 5 个，按偏移 0/2/4 取值。

**学到的**：**协议细节优先于代码技巧**。代码写得再漂亮，寄存器映射理解错一样全错。

#### ⑤ 偶发丢包（成功率 89% → 100%）

实测 `ok=32, err=4`，失败时连续 3 次全超时。定位到两个问题：

1. **日志说谎**：TX 打印写在重试循环外，实际发了 3 帧却只记录 1 次，导致误判"只发一次就失败"
2. **没有重试间隔**：上一帧总线未释放就发下一帧，自动方向切换的 485 电路容易丢帧头

修正：TX 打印移入循环内（每帧一条日志），重试之间加 20ms 间隔。修正后 `err=0`。

**学到的**：**日志记录的必须等于实际发生的**。日志不诚实，排查方向就会全错。

#### ⑥ Wi-Fi `reason=2` 与 `reason=201`

`reason=2` 是 AUTH_EXPIRE，首次认证瞬时失败；`reason=201` 是 NO_AP_FOUND，热点还没就绪。两者都在 1~3 秒内被自动重连恢复。

处理：认证方式从"仅 WPA2"放宽为 `WIFI_AUTH_WPA_WPA2_PSK`，声明 PMF 能力；同时在 `app_main` 里先 `wifi_wait_connected(20000)` 再启动上报通道，避免无网络时的无效连接重试。

**学到的**：区分"瞬时故障"和"持续性故障"。前者靠重连机制自愈，后者才需要改代码。

### 3.3 学会的知识

**协议层**

- Modbus RTU 帧结构：从机地址 + 功能码 + 数据 + CRC（低字节在前）
- CRC16 手工实现：初值 0xFFFF，逐位异或右移，多项式反转形式 0xA001
- 大端序与 ESP32 小端的区别，`struct` 拼接不能直接用 memcpy
- 异常应答：功能码最高位置 1，后跟异常码（0x01 非法功能 / 0x02 非法地址 / 0x03 非法数据 / 0x04 从机故障）
- 超时与重试要配合"总线间隔"，否则越重试越乱

**系统层**

- ESP-IDF 的事件循环模型：`esp_event_handler_register` + 回调，不要在回调里阻塞
- Wi-Fi 状态机：`init → auth → assoc → run`，只有 `GOT_IP` 才算真正可用
- FreeRTOS 任务：`xTaskCreate` 栈大小要按最坏情况估（cJSON + 深层调用），4096 是够用的起点
- `ESP_LOG` 分级：`E` 用于需要人干预的，`W` 用于可自愈的，`I` 用于正常流程

**工程方法**

- 分层验证：先跑 `hello_world` 证明环境没问题 → 再证明能烧录 → 最后写业务代码。每步只引入一个新变量。
- 交叉验证：CRC 用标准测试向量（`01 03 00 00 00 01 → 84 0A`）和离线独立计算双重确认，硬件没通就能确定软件正确。
- 失败路径要设计：超时、CRC 错、从机异常、Wi-Fi 断开，每种都要有明确行为且不中断主任务。

## 四、阶段一点五：追加 TCP 通道与开机自检

这一阶段不在三段式考核里，是主动补的两块。

### 4.1 TCP 通道

起因是文档里 UDP / TCP 术语前后矛盾。决策：**默认 UDP，TCP 作为可切换通道**，用 menuconfig 编译期三选一，不改代码。

TCP 相对 UDP 多出三个必须处理的点：

| 问题 | 处理 |
|---|---|
| 连接可能失败 | 首次发送时建连，带超时，失败不阻塞采集 |
| 断线后 socket "半死" | Wi-Fi 重连时主动 `close()`，下周期重建，否则 `send` 一直失败 |
| 粘包 | 每条 JSON 后加 `\n`，接收端按行切分 |

实测发现 TCP 的**半关闭**行为：对端进程崩溃但机器还在时，`send` 不会立刻报错，要等 TCP 重传超时。这个现象记在文档里，是网络编程里容易误判"程序没毛病"的坑。

### 4.2 开机功能码自检

写了一个 7 项自检模块，覆盖 `03` `06` `10` `04` `02` `01` 和异常码，每项最多 2 轮，整体约 45 秒。用途是**上板时先确认从机侧配置正确**，把"从机没配好"和"我的代码有问题"分开。

实测 4/7 通过，未通过的三项是 Modbus Slave 软件本身对 `0x`/`1x` 区支持不全，不是固件问题——这个结论是靠自检结果逐项对着软件功能判断出来的。

**学到的**：调试工具本身也会成为变量。与其猜"是不是从机没配对"，不如写个自检把答案打出来。

## 五、阶段二：MQTT 双向通信

### 5.1 完成的任务

| 要求（指导书 2.4） | 实现 |
|---|---|
| 连本地 broker，Client ID 用工号 | `esp-mqtt`，`client_id = CONFIG_MQTT_DEV_ID` |
| 周期发布 `data` | 每 5 秒一条，QoS 1 |
| 订阅 `read`/`write`，执行后回 `resp` | 订阅写在 `MQTT_EVENT_CONNECTED` 里 |
| 读写失败也要回 `resp` | 明确回 `result:"error"` + `msg` 原因 |
| 日志覆盖连接/请求/结果/上报 | 四个模块各管一段，`TAG` 区分 |

### 5.2 遇到的困难和解决过程

#### ① 回调里不能读 Modbus

一次 Modbus 读最坏要 200ms 超时 × 3 次 ≈ 600ms。如果在 MQTT 回调里同步读，协议栈任务就停摆 600ms，超过 keepalive（60s）会被判定离线；即使不超时，收发也会严重滞后。

方案对比：

| 方案 | 后果 |
|---|---|
| 回调里直接读 Modbus | 阻塞 → 心跳延迟 → 被踢下线 |
| 回调只入队，独立任务执行 | 回调 <1ms 返回，协议栈正常 |

代价是多一个任务（栈 4096）和一个队列（深度 8）。队列满时明确回 `request_busy`，而不是静默丢弃——上位机至少知道请求没被接受。

**学到的**：**回调是"传达室"，不是"车间"**。回调只做校验和分发，耗时操作交给自己的任务。

#### ② 采集任务和命令任务抢串口

加入命令通道后出现偶发 CRC 错和超时。原因是采集任务（每 5 秒）和命令任务（收到请求就发）会同时操作同一个 UART，两边的发送/接收互相穿插。

解决：给 Modbus 总线加互斥锁。

```c
static SemaphoreHandle_t s_bus_lock = NULL;

bool modbus_read_registers(uint16_t addr, uint16_t num, uint16_t *out)
{
    if (xSemaphoreTake(s_bus_lock, pdMS_TO_TICKS(MODBUS_BUS_WAIT_MS)) != pdTRUE) {
        return false;                    /* 等不到总线就放弃，不排队 */
    }
    bool ok = do_read(addr, num, out);
    xSemaphoreGive(s_bus_lock);
    return ok;
}
```

实测：命令超时期间（660ms），采集的 `ok` 计数继续增长、`err=0`，说明命令是**排队等总线**而不是把采集搞失败。

**学到的**：共享硬件的并发访问必须有明确的所有权，锁的等待时间要有限，不能让低优先级请求无限阻塞。

#### ③ 订阅写在错误的回调里

第一版把 `subscribe` 写在初始化函数里，结果是"能上报但收不到命令"。原因是默认 clean session 不保留会话，断线重连后订阅关系全部丢失，而初始化只执行一次。

修正：订阅放进 `MQTT_EVENT_CONNECTED` 回调，每次（含重连）连上就重新订阅。

**学到的**：MQTT 的订阅关系是**会话级**的，不是连接级也不是永久级。clean session 下重连即丢。

#### ④ 分片载荷必须整条丢弃

超过接收缓冲的载荷会被 esp-mqtt 拆成多片，每片单独回调一次，此时 `data_len` 只是分片长度、`total_data_len` 才是整条长度。

如果拼残片，JSON 可能"恰好"被解析成功——从而执行一条本该被拒绝的命令。所以判断 `total_data_len != data_len` 直接整条丢弃并记日志。

**学到的**：宁可丢一条，也不能执行一条错的。

#### ⑤ 坏 JSON 无法回应答

`req_id` 在 JSON 里不在，解析失败时取不到，无法组一条带 `req_id` 的应答。硬编一个假的 `req_id` 会让客户端误配对。

处理：只记日志丢弃（`bad json on dev/intern01/read`），进程不重启。这正是 M-07 要求的行为。

#### ⑥ `req_id` 严格白名单

```c
/* 只允许字母数字下划线连字符 */
if (n == 0 || n >= CMD_MAX_REQ_ID) return false;
for (...) {
    bool ok = (c >= 'a' && c <= 'z') || (c >= 'A' && c <= 'Z') ||
              (c >= '0' && c <= '9') || c == '_' || c == '-';
    if (!ok) return false;
}
```

这样 `req_id` 拼进 JSON 时**不可能注入引号或反斜杠**，省掉了为转义去动态分配内存——在只有 400KB 可用堆的 MCU 上，这个约束换的是"不会被构造出的恶意 `req_id` 撑爆内存"。

#### ⑦ 分区不够了

阶段二代码量上来后，默认 1MB 的 app 分区只剩 4% 余量（44,016 字节），编译开始报分区溢出。

解决：`CONFIG_PARTITION_TABLE_SINGLE_APP_LARGE`，app 分区 1MB → 1500K。关键点是 `nvs` 偏移仍是 0x9000，所以**Wi-Fi 凭据没有丢**（冷启动 7608ms → 热启动 1838ms 可证）。

同时踩到一个坑：改了分区表必须**连 partition-table.bin 一起重烧**，只烧 app 不够。

#### ⑧ MQTTX 收不到数据（三个独立原因叠加）

排查时一次撞上三个问题：

1. 订阅主题是阶段一遗留的 `inverter/#`，而固件发的是 `dev/intern01/data`——`#` 通配符只能从当前层级往下匹配，不会跨到 `dev/` 这棵树
2. 发送框主题还是 `inverter/collector/data`，没有任何人订阅
3. 载荷缺 `req_id`/`slave`/`addr` 等必需字段

**学到的**：主题是"地址"，通配符只在当前节点往下生效。"订阅了 `#` 就等于全收"是错的。

#### ⑨ 测试脚本自己的时序 bug

`cmd_probe.py` 偶发丢 `resp`（4 秒超时）。根因不是固件，是脚本在 `on_connect` 里连着调 `subscribe` 和 `publish`——SUBACK 还没回来就发请求，板子应答太快时客户端侧订阅尚未生效。

修正：拆到 `on_subscribe` 回调里发请求，等待时间 4s → 6s。

**学到的**：**测试工具本身也会有 bug**。出现"偶发失败"时，先证明工具是可靠的。

#### ⑩ QoS 1 的重复投递

实测中 5 次测试有 1 次收到 2 条 `resp`，最多见过 4 条。串口日志证明板子每次只执行一次——重复发生在 broker 到订阅者的投递环节。

这是 QoS 1 "至少送达一次"的正常语义。业务层必须靠 `req_id`（应答）或 `seq`（上报）去重。

**学到的**：QoS 1 保证的是"不丢"，不是"不重"。要"不重"得用 QoS 2，或者自己在业务层做幂等。

### 5.3 学会的知识

**协议层**

- 发布/订阅模型：设备和客户端都连 broker，彼此不直连，靠主题解耦
- 四个概念的职责：Broker 转发（唯一固定地址）/ 发布订阅（不指定收件人）/ Topic（地址+过滤器）/ Client ID（身份）
- Client ID 重名后果：后连的踢掉先连的，两边无限互踢
- clean session 与订阅持久性：clean 下重连即丢订阅
- QoS 0/1/2 的取舍：0 最多一次、1 至少一次、2 恰好一次（握手轮次递增）
- MQTT 协议层没有"请求-应答"概念，只能靠载荷里的 `req_id` 自己配对

**系统层**

- 互斥锁保护共享外设，等待时间必须有限
- 队列做任务间解耦，容量和"满了怎么办"都要设计
- 回调上下文与任务上下文的区别（能不能阻塞、栈多大）

**工程方法**

- 边界安全：长度先校验再拷贝，topic 不以 `\0` 结尾必须按长度比较
- 主题用宏在编译期拼接，改工号一处生效
- 敏感信息全部走 Kconfig，源码不含凭据

### 6.2 遇到的困难和解决过程

#### ① Windows 上没有 protoc-c 的官方二进制

`protobuf-c` 官方 release 只提供源码包（v1.5.2 / v1.3.3 都是 `.tar.gz`），没有 Windows 预编译的 `protoc-gen-c.exe`。

尝试路径与结果：

| 途径 | 结果 |
|---|---|
| PyPI 清华镜像装 protobuf | HTTP 403，换官方源成功 |
| MSYS2 清华镜像 | HTTP 403 |
| MSYS2 USTC 镜像 | 没有 protobuf-c 包 |
| MSYS2 官方 `repo.msys2.org` | ✅ 可用 |

最终从 MSYS2 官方仓库下载四个包，从 `pkg.tar.zst` 里解出 `protoc-gen-c.exe` 和它依赖的 DLL（`libprotobuf-c-1.dll`、`libprotoc.dll`、`libabsl_*.dll` 等）。

坑中坑：`cc-libs` 是 2KB 的元包，真正的运行时 DLL 在 `gcc-libs` 里。

#### ② 版本兼容性（这个必须先确认，否则生成完编译不过）

生成的 C 代码里有：

```c
#if PROTOBUF_C_VERSION_NUMBER < 1003000
#error This file was generated by a newer version of protoc-c ...
#endif
```

本机工具链是 `protoc` 6.30.2 + `protoc-gen-c` 1.5.2，而 IDF 5.5.5 自带的运行时是 **protobuf-c 1.4.1**（`1004001`）。`1004001 > 1003000`，满足要求，**不需要改任何一行生成代码**，也不需要升级 IDF 组件。

**学到的**：跨工具链的项目，先确认版本门槛，再动手生成。否则会把"版本不兼容"误判成"自己代码有问题"。

#### ③ `metrics` 是双层指针

生成的 `Telemetry` 结构体里，`metrics` 的类型是 `Metric **`（指针数组）+ `size_t n_metrics`，不是数组本身。所以要两层分配：

```c
Metric  *metrics = calloc(n, sizeof(Metric));
Metric **ptrs    = calloc(n, sizeof(Metric *));
for (int i = 0; i < n; i++) {
    metric__init(&metrics[i]);
    metrics[i].addr = ...;
    ptrs[i] = &metrics[i];
}
t.n_metrics = n;
t.metrics   = ptrs;
/* pack 之后再 free(ptrs); free(metrics); */
```

用 `calloc` 不用 `malloc`，是为了让未显式赋值的字段是 0，符合 proto3 的默认值语义。

#### ④ `strlen` 会截断二进制

发布时如果按文本习惯传 `strlen(payload)`，报文里第一个 `0x00` 就会把长度截断。而 `0x00` 在这种报文里**很常见**：

- `raw = 0` 时字段直接不编码（proto3 默认值）
- 浮点数的尾数字节：`5.0` 的编码是 `1d 00 00 a0 40`，中间两个 `00`

实测 `raw=0` 那一帧是 50 字节，含多个 `0x00`，按 `strlen` 量会截成半条，对端 `unpack` 直接失败。

修正：所有发布统一传 `pack` 返回的真实字节数。

**学到的**：**一旦载荷是二进制，长度就必须显式传递，不能靠任何字符串函数推断。**

#### ⑤ `free_unpacked` 容易漏

`unpack` 出来的结构体内部有动态分配，必须 `free_unpacked`。但解码函数有多个返回分支（长度错、解包失败、req_id 非法、字段越界），每个分支都写一次释放很容易漏一个。

处理：用 `goto done` 把释放集中到一个出口。

```c
ReadRequest *req = read_request__unpack(NULL, len, data);
if (req == NULL) return CODEC_ERR_UNPACK;
...
done:
    read_request__free_unpacked(req, NULL);   /* 任何路径都执行 */
    return result;
```

#### ⑥ 指导书的 P-06 用例本身是错的

指导书让发 `0a0131` 来演示 "`unpack` 返回 NULL"。但 **proto3 没有 required 字段**，这 3 个字节是一条完全合法的报文：`req_id="1"`，其余字段取默认值 0。所以 `unpack` 会成功，然后被"`slave` 必须在 1~247"的范围校验拦下。

实测两条路径：

| 输入 | 结果 |
|---|---|
| `0a0131` | 解码成功 → 范围校验拦截 → 回 `resp{ok=false, msg="invalid_param"}` |
| `0a0531`（长度字段声明 5、实际 1 字节） | `unpack` 返回 NULL → 记日志丢弃 |

顺便改进了一处：原本 `req_id` 只在校验全部通过后才拷出，导致越界请求拿不到 `req_id`、只能像坏报文一样静默丢弃。把拷贝挪到范围校验之前后，越界也能回带 `req_id` 的错误应答。

**学到的**：**文档和规范也会错**。发现用例行为和预期不符时，先判断是"我实现错了"还是"用例本身基于错误的前提"。

#### ⑦ MQTTX 用错了 message 类型解码

MQTTX 的 protobuf 视图把 `Telemetry` 帧按 `Metric` 解，显示成 `{addr:0, raw:1515, value:0}`，看着像成功。

原因：`Telemetry` 和 `Metric` 的字段号撞车（1/2/3 号字段名不同但号相同），而 protobuf 遇到**类型不符的字段是跳过、不报错**。所以 `raw` 读到的其实是 `seq`（都是 varint），`addr` 和 `value` 因为线路类型不匹配而保持默认值 0。

验证方法：把同一段字节按 `Metric` 解，得到的结果和界面完全一致；`1515` 正好是当时的 `seq`（16:37 读到 `seq=1665`，14 分钟 165 帧，时间对得上）。

**学到的**：**二进制协议解错不会报错**。字段号对不上是跳过、类型对不上也是跳过，解出来的对象照样能打印，只是全是默认值。所以必须有独立可信的解码工具做对照。

#### ⑧ PC 端解析脚本的"判断报文类型"没那么简单

第一版用"能解出来且编回去一致"来判断类型，结果一段 `Resp` 被误判成 `Telemetry`——因为两份 message 字段号重叠，对不上的字段被当"未知字段"保留，往返比对同样成立。

改成扫顶层 tag 判断 `(字段号, 线路类型)` 是否与 schema 完全吻合，再加两条语义过滤：

- `Telemetry` 必带 `metrics`（字段 5）和 `ts_ms`（字段 3），否则不可能是本工程的上报帧
- `ReadRequest.num` 固件上限 16，字段 4 的值超过 16 就只能是 `WriteRequest.value`

剩下 `ReadRequest` 与 `WriteRequest` 结构完全一致，无法自动区分，脚本会明确提示"结构上也吻合，只能结合主题判断"。

#### ⑨ 烧录波特率不稳

460800 下报 `chip stopped responding`，`--no-stub` 115200 写到 15% 报 `message format invalid`。改用 **stub + 115200** 成功（997,280 字节，57 秒）。

另外 ESP32-C3 **不支持 esptool 的软件复位**（`Soft resetting is currently only supported on ESP8266`），四线线又没有 RTS，所以烧完必须手动按 RST 才能跑起来。

### 6.3 学会的知识

**协议层**

- wire format：每个字段 = `tag` + 值，`tag = (字段号 << 3) | 线路类型`
- 线路类型：0 变长整数 / 1 64 位定长 / 2 长度前缀 / 5 32 位定长
- varint 编码：7 位一组、低位在前，值越小占字节越少（`seq=994` 占 2 字节，`seq=6` 占 1 字节）
- packed 编码：`repeated` 数值默认打包，一个 tag + 一个总长度 + 连续值
- 字段号 1~15 的 tag 占 1 字节，16~2047 占 2 字节，所以热字段排前面
- 字段号发布后不可改、不可复用，废弃要用 `reserved`
- proto3 默认值不编码——`value=0` 时整个字段消失，所以"写 0"的请求只有 8 字节

**工程层**

- 生成文件要入库（否则没装 protoc-c 的人无法编译）
- 编解码要封一层，上层不碰 `pb-c.h`：内存所有权、长度语义、错误码都收在一处
- SNTP 对时：`ts_ms` 用真实 Unix 毫秒，未对时退化为开机毫秒，字段永远有值
- 同一份 `.proto` 同时生成 C 和 Python，两端字段号天然一致

**调试层**

- 二进制协议的取证方法：原始 hex + 独立解析器 + 逐字节往返比对
- 长度语义错误的表现是"对端解不出来"，不是"本地报错"——所以要在对端验证

## 七、贯穿三个阶段的技术主线

回头看，真正反复出现的不是某个 API，而是六条方法：

### 1. 分层验证，一次只引入一个变量

`hello_world` 编译通过 → 能烧录 → 能从机应答 → 能上报。每一步都把上一层当成"已验证的黑盒"，问题就不会串在一起。

后期把这个方法用到了工具链上：先单独验证 `protoc` 能生成、能编译，再接业务代码。

### 2. 日志要诚实

TX 日志放在循环外导致误判"只发一次就失败"，多花了半天。教训是日志记录的次数、时序必须与实际一致。

### 3. 每条失败路径都要有明确行为

| 失败 | 行为 |
|---|---|
| Modbus 超时 | 重试 3 次，仍失败则上报 `state=1` 并沿用上次值 |
| 从机异常码 | 翻译成 `modbus_illegal_address` 等可读原因回给上位机 |
| 坏 JSON / 坏 protobuf | 记日志丢弃，不重启（取不到 req_id 无法配对） |
| 队列满 | 回 `request_busy`，不静默丢弃 |
| Wi-Fi 断开 | 跳过上报但继续采集，恢复后自动续传 |
| broker 断开 | esp-mqtt 自动重连，重连后重新订阅 |

### 4. 边界安全：长度先校验，再解析/拷贝

三个阶段都在做同一件事：拷之前先量。

- 主题不以 `\0` 结尾 → 按长度比较，不 `strcmp`
- 载荷先判长度上限（512），再 `unpack`
- `unpack` 返回 NULL 必须判空
- 二进制发布传真实长度，不传 `strlen`

### 5. 内存所有权要明确

每个 `malloc` 都有配对的 `free`，而且放在同一个函数里：

| 场景 | 分配 | 释放 |
|---|---|---|
| Telemetry 测点 | `calloc` 两层 | pack 后立刻 `free` 两层 |
| 编码结果 | `pack_message` 内 `malloc` | 调用方 `codec_free` |
| 解码结构体 | `unpack` 内部分配 | `free_unpacked`（`goto done` 保证） |

### 6. 协议细节优先于代码技巧

寄存器步长为 2、字段号不能复用、QoS 1 会重复投递、订阅是会话级的——这些"协议事实"理解错了，代码写得再优雅也是错的。

## 九、学到的东西（分四层）

### 协议层

Modbus 帧结构与 CRC16、MQTT 发布订阅与 QoS、protobuf wire format。三者有一个共同点：**都是"字段号 / 地址 / 主题"驱动的，不是"名字"驱动的**。理解了这一点，三种协议的设计思路其实是同一套。

### 系统层

事件驱动与阻塞的边界、任务与队列的分工、共享外设的互斥、堆与栈的预算（400KB 可用堆下要避免大缓冲和动态转义）、分区表的空间规划。

### 工程方法

分层验证、交叉验证、失败路径设计、日志诚实性、边界安全、文档与代码同步（每次改动都更新 README 和测试报告）。

### 调试手段

- **隔离变量**：把"环境问题"和"代码问题"彻底分开
- **交叉验证**：CRC 用标准向量、协议用独立解析器、数值用串口日志对照云端
- **自己造工具**：`build_run.py`（绕开 PowerShell 管道卡顿）、`watch_serial.py`（中文不乱码）、`cmd_probe.py`、`proto_decode.py`、`modbus_slave_sim.py`（脚本化从机，替代图形界面）

最后一条体会最深：**工具决定了排查的速度**。用 MQTTX 手点，改一个测试步骤要 30 秒；用脚本从机 + 解析脚本，一轮 3 秒，还能留下可复现的日志。
